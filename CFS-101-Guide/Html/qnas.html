Task Scheduling with the sch Application

  • How does sch schedule my task to run at a certain rate?

To signal an app to run at some specified frequency, SCH sends it WakeUp messages at that frequency. If an app receives WakeUp messages at a rate of 1 msg/sec,then its execution frequency is at 1Hz. If it receives them at a rate of 40 msg/sec, then its execution frequency is expected to be at 40Hz.

ONLY upon receiving a WakeUp message can an app get to run through its processing cycle, exactly once per WakeUp message. At the end of a cycle, the app goes back into listen mode, awaiting for another WakeUp message to run through another cycle.

  • How does SCH coordinate the sending of messages to different apps at different rates?

SCH makes use of two tables for that very purpose. One table, sch_def_msgtbl, defines the list of messages (and their packet definition) that SCH can send (so yes, SCH can send other messages as well, not just WakeUp messages). The other table, sch_def_schtbl, defines the scheduling of those messages. In the sch_def_schtbl table you would provide table indices where the messages are defined in the sch_def_msgtbl table. From the table indices, SCH can get to their packet definitions.

In a nutshell, SCH works like this: It registers itself to your mission’s major and minor frame interrupts. A major frame interrupt puts the sch_def_schtbl table at slot #0, i.e., minor frame #0. A minor frame interrupt puts the sch_def_schtbl table at the next slot (i.e., the next minor frame). When an interrupt is received and the table slot number is determined, SCH will send out all the messages defined in that table slot.

The size of the sch_def_schtbl table traditionally matches the mission running rate. So if your mission is designed to run at 40Hz (i.e., 40 minor frames/major frame) then the size of the sch_def_schtbl table should be 40 (i.e., 40 table slots). If an app is to run at 1Hz, there should be exactly one WakeUp message defined in exactly one of those 40 table slots. For an app running at 20Hz, there should be exactly 20 WakeUp messages in exactly 20 evenly spaced table slots, i.e., either all even slots or all odd slots.

  • How does SCH handle task priorities? Does it preempt my app from running for higher priority apps to run?

SCH does not meddle with task priorites. It does not replace your traditional OS task scheduler, which can preempt a task from running. It works in conjunction with your OS task scheduler. It coordinates the sequence of execution by dictating WHEN an app (or task) can run by sending WakeUp messages at specified times. When multiple apps are running in the same minor frame (i.e., multiple apps receiving WakeUp messages about the same time) it is the OS task scheduler that controls which one runs based on their designated task priorities.

It is the system engineer’s job to manually tweak the sch_def_schtbl table to achieve mission performance. For example, if an app is known to take three minor frames to complete one processing cycle it should not be scheduled to run at 40Hz or even 20Hz. If it is so scheduled, that app will run continuously and indefinitely within the cFS framework because it continuously receives WakeUp message at the end of every processing cycle. Along the same line, if an app is required to run at 20Hz then its processing cycle time should be less than the duration of two minor frames.

cFE Tables

  • What is a cFE table? When should I use tables in my app?

A cFE table, in a nutshell, is simply another global variable to the app whose type can be a single array, a multi-dimensional array, a simple data structure, or even a very nested data structure. It typically stores constants (default or initial values) used by the app. It is defined such that it is compiled separately from its app and is loaded by its app during the app’s startup stage. It can also be re-loaded during run time, providing the app with a new set of values in the middle of a system run.

You should use tables if you have a requirement to update a set of data during run time or a last minute update prior to startup. In those cases, only the affected tables need to be re-compiled and re-loaded - not the entire code set.

Note that cFE tables are considered part of an app’s source code. They are not considered data files.

Data Exchange with the Software Bus

  • How many message pipes can an app have?

An app can have as many message pipes as necessary, as long as the cumulative number of message pipes created for your mission is less than the maximum number of message pipes set at the OS level.

  • How do I determine how many message pipes my app needs? And how deep of a message queue?

First of all, message pipes are for subscriptions only. An app does not need a message pipe to send out data.

An app can run sufficiently with 3 message pipes: 1 for messages from the SCH, 1 for commands either from ground or other apps, and 1 for telemetry from other apps. The depth of each message queue can be determined by the total number of subscribed messages expected. For example, an app running at 1Hz subscribes to messageA, published at 1Hz, and messageB, published at 10Hz. Then in one processing cycle the app will receive 1 messageA and 10 messageB. So the depth of its telemetry pipe should be atleast 11 to avoid incoming messages being dropped.

There are cases where multiple telemetry pipes are needed to handle both periodic and change-only data. Since message pipes used by cFS framework are FIFO queued, an app must process every single message posted in its queue. When the queue is full, incoming messages will be dropped until there is room in the queue again. This might be okay with periodic data, but not for change-only data. For this reason, periodic data should not be packed in the same telemetry message with change-only data, and should not be received in the same message pipe.

Distributed Run-Time Environment

  • Is a cFS system a distributed system?

Not really.

On Linux, cFS system runs as a single process. But it is a multi-threaded process, where each app runs as a Posix child thread. In a real-time environment like VxWorks, an app runs as a VxWorks task (which, in many ways, works like a Posix thread).

Data exchange among the threads or tasks is through the Software Bus service, which makes use of system message pipes, and not network services. The only network services being used is through the two designated apps, CI and TO, specifically for communications with the ground system. The sole function of CI is to receive commands (and tables) from the ground and put them out on the Software Bus for the other apps to consume. The sole function of TO is to subscribe to other apps' telemetry and downlink this telemetry to the ground.

  • Can I setup my cFS system to run in a distributed environment?

Absolutely!

Although you can’t have your apps running on multiple network nodes, you can run a network of multiple cFS systems. A ground system can be set up to interact with all of them through their CI and TO apps. To exchange data between cFS systems, include an app called SBN (Software Bus Network).

Interacting with the Ground System

  • What ground system tools work with the cFS system?

Any ground system tool that can properly encode and decode CCSDS messages should work with the cFS system. We’ve seen and used tools like cFS-GroundSystem (packaged with cFE), YAMCS (Yet Another Mission Control System), ITOS (Integrated Test and Operations System), COSMOS, and a few stand-alone display applications.
